# R26-245 — a KEN is the row's life, and the counter says which

**The defect.** R26-236 withdrew the painted drift for long form on the operator's word (E99 s84:
"the drift is too random, i think we should use ken burns instead of drift"). A long-form plate row
therefore carries `;use=landing`, a ken tuple, and **no `;idle=` token at all**. Both of the H
build's counters — the printed report and `SHOT-TABLE-H.md` — read only the `;idle=` token, so the
bed's report said `idle tokens: 1 of 2 rows` about a cut in which **every row was alive**. E49's
floor is that nothing goes truly still; the counter was contradicting it on a row that was correct.

**The fix.** `authoring.table.life_tokens(rows)` — the reader lives beside the row grammar it reads
(`ROW_KEN = 3`, the 4th element of the tuple documented in that module's own docstring) and returns
`(row number, what carries it)` for every row that carries any life. A ken of all zeros is no push
and no life, so the reader can still say a row is dead. Both call sites in `build_episode_h.py` now
print `life`, never `idle tokens`.

**Measured on the bed's own authored table** (`build-h/SHOT-TABLE-H.py`, read without rebuilding):

| | |
|---|---|
| before | `idle tokens : 1 of 2 rows (1)` |
| after | `life : 2 of 2 rows (row 1 idle=live; row 2 ken 0.04/10/-6)` |

**No gate changed, and that is a measurement, not an assumption.** M18 is the idle's own check and
it reads the RENDERED frames (`gate_motion_density._frozen_gate` over `frame-hashes.json`) — a ken
push moves pixels, so the gate was never fooled by the withdrawn drift. The defect was only ever in
the build's own report of itself.

**Tests** (`test_authoring_kit.py`, four rows): a ken-only plate row is life and the reader names it;
a painted idle is still life and a row may carry both; a zero ken with no idle is no life; a short
row and a junk ken do not raise. Suite: 84 passed in `test_authoring_kit.py`.
